# Layer 1 signal collector - physics & engineering reality

Collects dated, sourced early-stage physics/engineering signals: arXiv paper clusters on a
tracked hardware bottleneck, HackerNews/engineer-community threads discussing the same bottleneck,
conference-topic signals, patent filings, GitHub/Hugging Face adoption velocity, government R&D
grants, manufacturing-enablement partnerships, lab/university spinouts carrying a research signal,
and customer-usage-growth wording. Discovery only: nothing here prices, tiers or judges a stock.

Funding rounds, IPOs and fund positions are Layer 4; contracts, capacity and procurement are
Layer 3; a named person hired/appointed/departing is Layer 2's own event - Layer 1 only creates
its own `spinout_signal` row when the SAME event also carries a research signal, and
cross-references Layer 2's row instead of duplicating the person fact (see "Boundary rules"
below). This is deliberately the opposite emphasis from Layer 2/3/4: those layers are
filing/press-driven (an 8-K, a press release); Layer 1's whole premise is catching the signal
*before* any filing or press release exists, so arXiv/HackerNews/GitHub/Hugging Face are
first-class direct-API collectors here, not items lumped into the generic feed list.

## Two layers of capture

1. **Wholesale.** Every arXiv entry (by tracked category, newest-submitted first), HackerNews
   hit, GitHub/Hugging Face result, SEC full-text hit and feed item that is reachable is stored
   with its date, source and link before any filter is applied.
2. **Keyword combinations.** Each stored item's text is analysed sentence by sentence (same
   mechanism as Layer 2/3's engine - see `config/keywords.json`): a research marker + a tracked
   bottleneck term; an engineer-community marker + a bottleneck term; a conference term; a patent
   marker; a government R&D marker (explicitly excluding Layer 3's procurement/capacity wording);
   a manufacturing-partnership term (excluding Layer 4's funding wording); a lab/university
   spinout carrying a research or pedigree-institution marker (excluding funding wording);
   customer-usage-growth wording. Score = strongest combination + 1 per further distinct
   combination (max +3); kept when score >= the keep threshold in `keywords.json`.

**Important asymmetry, found during testing (2026-10-17) - read before changing the gate logic.**
For the arxiv/hn/github/hf/patents modules, a kept item is **not** required to already map to a
tracked ticker or private-watchlist company (`gate_relevance` is deliberately not applied to
them). Layer 1's whole premise is catching a bottleneck signal *before* it is tied to any company
- gating on today's tracked universe would filter out exactly the earliest, not-yet-mapped signals
routine 01's agents exist to map to a company. `gate_relevance` (ticker/sector/private-watchlist
required) is applied only to `feeds` and implicitly to how `fts` hits are read, because news/press
items are almost always already about a named company, so ungated text there is mostly noise.
This was a real bug caught by running the collector, not a design assumption: the first test run
had `arxiv_kept: 0` out of 196 entries with the gate on; removing it for the topic-based modules
produced 66 genuine candidates (RISC-V accelerators, FPGA designs, GPU-isolation papers, etc.)
from the same day's data.

## Boundary rules with Layer 2 and Layer 3

- **`spinout_signal` (here) vs `departure_to_found` (Layer 2).** Layer 2 owns the person fact
  (who left, from where, to found what). Layer 1 only creates a row when the *same* event also
  carries a research/engineering signal (the founding team's own prior arXiv paper, a named
  pedigree institution) - and that row cross-references Layer 2's row rather than re-describing
  the person move.
- **`gov_rd_signal` (here) vs `gov_award` (Layer 3).** Layer 3's `gov_award` is a
  procurement/capacity contract (buying something at production scale: MW, units, delivery
  dates). Layer 1's `gov_rd_signal` is an R&D grant/award funding research toward something with
  no commercial product yet (DARPA, NASA SBIR, a cooperative agreement). The `gov_rd_signal`
  combo explicitly excludes sentences also matching `procurement_exclude_terms` (megawatt,
  gigawatt, units delivered, production order, power purchase agreement) so the two layers do not
  double-count the same government dollar figure.

## What runs when

| Job | When (New York) | Started by | Writes |
|---|---|---|---|
| Daily collector | Every day **11:45 PM ET** (L4=11:00 PM, L3=11:15 PM, L2=11:30 PM - 11:45 keeps the four apart) | routine 00a pushes `triggers/daily.txt` -> GitHub Action `Layer 1 - daily collector` (`.github/workflows/layer1-daily.yml`) | `data/daily/...` |
| Weekly packet | **Friday** 12:00 AM (window Friday-Thursday, folder named for the Thursday it closes - same convention as Layer 2's Thursday-run/Wednesday-named packet) | routine 00b pushes `triggers/weekly.txt` -> GitHub Action `Layer 1 - weekly packet` (`.github/workflows/layer1-weekly.yml`) | `data/weekly/<Thursday>/` |
| Routines 01-04 | Friday 1:00-4:00 AM | claude.ai routines | `research/layer 1/signal-discovery/<end-date>/` |
| Routines 05-07 | Friday 5:00-7:00 AM | claude.ai routines | `research/layer 1/signal-deepdive/` |

Friday was chosen so the four layers' weekly cadences don't collide: L4=Tuesday, L3=Wednesday,
L2=Thursday, **L1=Friday**.

Manual run from this folder:

```
python tools/build_feeds.py                           # after editing sectors.csv or the feed list
python layer1_daily.py                                # all modules, last run's seen-items excluded
python layer1_daily.py --only arxiv,hn                # just the two zero-auth API modules
python layer1_daily.py --only feeds --fresh            # feeds only, ignore the seen-items list
python layer1_daily.py --only patents --patents-budget 2   # USPTO ODP if the key is set, else best-effort - see "Known limits"
python layer1_weekly.py --end-date 2026-10-16          # packet for the window ending that Friday
python tools/test_sources.py                           # re-test every source live
```

Requirements: Python 3.10+, `openpyxl`. No API keys required for the dependable modules.
Network: export.arxiv.org, hn.algolia.com, api.github.com (unauthenticated, ~60 req/hr - the
collector queries a small rotated set, well under that), huggingface.co, efts.sec.gov
(full-text, secondary use), trade-press RSS, news.google.com. Environment variable
`USPTO_ODP_API_KEY` (registered, set as a GitHub Actions repository secret 2026-10-17) makes
patent coverage dependable via USPTO's Open Data Portal (see below); without it, `run_patents()`
falls back to the best-effort Google Patents scrape.

## How the vocabulary was built and tested

* Source: word and phrase counts of 3,129 Layer 1 Deal-signal sections (across 3,337 published
  pages) from the retired `hf-signal-framework` process (counted only; that process is not used
  otherwise), plus the old Layer 1 methodology page's own named search terms (arXiv/HackerNews
  keyword lists, patent search strings, daily headline/stealth-launch phrases, conference
  calendar, development areas).
* Live-tested against real arXiv/HackerNews/feed data on 2026-10-17 (not just unit-tested against
  old text): the first `arxiv` run returned 0 kept items out of 196 real entries; removing the
  company-relevance gate for topic-based modules (see "Important asymmetry" above) produced 66
  genuine candidates from the same data. A `toms_hardware` feed item falsely fired
  `conference_signal` because the RSS summary field carries a sitewide "Go deeper with TH
  Premium" boilerplate block naming unrelated conferences (GTC, Computex) on every article; fixed
  by adding that phrase to `sentence_veto`. The `spinout_signal` combo missed a present-tense
  "spin out of" phrasing on first test; added. The `fts_queries` list originally used
  two-exact-phrase AND-combinations that returned 0 hits over a 9.5-month SEC full-text window;
  replaced with the single/looser phrases that actually return hits (`"patent portfolio"`: 476
  hits in 3.5 months; `"cooperative agreement"`: 41; `DARPA` alone: 101).
* A full end-to-end run (all 6 dependable modules) completed in 2.4 minutes and produced a real
  weekly packet (130 signals, `packet.xlsx` included) from one day of live data - see `data/`
  (this is a one-day test, not seven days of real history; the real schedule accumulates one
  day at a time from here).

## Known limits (stated, not hidden)

- **Patents are dependable via USPTO ODP, as of 2026-10-17.** `USPTO_ODP_API_KEY` is registered
  and set as a repository secret; `run_patents()` uses it as the primary source and only falls
  back to the best-effort Google Patents scrape when no key is present (for example a local run
  without the env var set).
- **LinkedIn hiring/job-posting signals are agent-covered, not scripted** - confirmed login-walled
  for a scripted client even though the page returns HTTP 200.
- **G2/Gartner/SimilarWeb/BuiltWith (the usage_growth_signal's richest sources) are agent-covered**
  - 403 or JS-rendered shell to a scripted client.
- **arXiv/HackerNews/GitHub/Hugging Face items routinely have no tracked ticker or private-company
  match** - this is by design (see "Important asymmetry" above), not a bug; it means routine 01's
  agents have real company-mapping work to do on a meaningful fraction of each week's candidates,
  which is exactly Layer 1's job.
- **GitHub API rate limit (~60 req/hr unauthenticated)** - the collector queries a small rotated
  set of adoption terms per run, staying well under it; do not widen the query list without also
  adding a token.
- **SEC full-text search is secondary/corroboration only for Layer 1** - unlike Layer 2/3/4, it is
  not the primary daily source.
- **Conference-calendar dates are approximate** (`config/conference-calendar.csv`) - verify exact
  dates each year; the module only flags that a tracked conference's window is open, not what is
  actually on its programme.
